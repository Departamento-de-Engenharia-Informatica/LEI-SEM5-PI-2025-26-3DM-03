# User Story 3.5.1 – Automated Deployment Process  
### Systems Administration & Business Continuity  
---

## 1. Overview  
**User Story 3.5.1**  
*As a System Administrator, I want a systematic and automated deployment process for one of the system modules to a controlled DEI environment (e.g., VM or containerized setup), so that deployments can be validated regularly using the test plan.*

This document describes the implemented automated deployment pipeline, its architecture, validation steps, scheduling configuration, and how traceability and reproducibility are ensured.

---

## 2. Objectives  
The deployment process must satisfy the following requirements:

- Fully automated CI/CD deployment pipeline  
- Automatic execution of validation steps (tests)  
- Deployment logs & test results archived for traceability  
- Reproducible, isolated deployment environment  
- Configurable deployment schedule (manual, nightly, weekly)

The implemented solution fulfills all mandatory Acceptance Criteria.

---

## 3. Deployment Architecture

### 3.1 CI/CD Pipeline  
Deployment is handled by a **GitHub Actions workflow** named:  
```
deploy-todoapi.yml
```

This pipeline is responsible for:

- Building the system module (TodoApi)
- Running automated tests
- Packaging the module as a Docker image
- Deploying to the controlled **DEI VM environment**
- Validating the deployment
- Archiving logs for traceability

### 3.2 Controlled Deployment Environment  
The system module is deployed into a **containerized environment** on the DEI VM:

- Single controlled VM  
- Uses Docker runtime  
- Deployment script stops old container safely  
- Pulls new version from private GHCR registry  
- Starts the service exposing port 8080  

This ensures **isolation**, **reproducibility**, and **clean rollback capability**.

---

## 4. Deployment Pipeline Breakdown

### **Job 1 — Build & Test**  
Executed automatically on each run.

Steps include:

1. Checkout code  
2. Restore dependencies  
3. Build the module  
4. Run automated tests defined in the test plan  
5. Export test results  

✔ *Ensures validation happens on every deployment.*

---

### **Job 2 — Containerization**  
Builds a Docker image using:

```
docker/build-push-action@v5
```

Key features:

- Reproducible build  
- Image tagged with commit hash and timestamp  
- Pushed to GHCR private registry  
- Summary logs exported for traceability  

✔ *Ensures consistent builds and secure storage.*

---

### **Job 3 — Deployment to DEI VM**  
A GitHub-hosted runner remotely connects to the DEI VM.

Deployment includes:

- Authentication into GHCR
- Pulling latest image
- Verifying Docker layers
- Stopping the previous container (`todoapi`)
- Starting the new one:

```
docker run -d -p 8080:8080 --name todoapi <image>
```

✔ *Ensures automated and safe rollout.*

---

### **Job 4 — Summary Logging**  
A final summary job:

- Collects test logs  
- Collects deployment logs  
- Packages them as workflow artifacts (Long-term traceability)  

✔ *Allows full auditability of deployments.*

---

## 5. Automated Validation (Test Plan Integration)

The pipeline runs automated tests described in the project test plan (unit + integration tests).

Validation includes:

- Build failure detection  
- Test result validation  
- Deployment container health check  
- Port availability check (8080)  

If any step fails → **deployment is automatically aborted**.

✔ Supports continuous validation.

---

## 6. Traceability & Log Archival

Each pipeline execution stores artifacts:

- **Container build logs**  
- **Deployment logs**  
- **Test results**  
- **Metadata:** commit, timestamp, image tag  

Artifacts are accessible in **Actions → Run → Artifacts**.

✔ Meets traceability requirement.

---

## 7. Reproducibility & Isolation

Reproducibility is ensured via:

- Clean ephemeral GitHub runner for each job  
- Deterministic Docker builds  
- Isolated container on the DEI VM  
- Fixed dependencies & environment variables  

Isolation:

- Environment separate from development machines  
- Container runs with isolated filesystem  
- No side effects on host OS beyond Docker engine  

✔ Ensures consistent, isolated deployments.

---

## 8. Deployment Scheduling Configuration

The workflow supports:

### **Manual dispatch**
The System Administrator can run deployments anytime:

```
workflow_dispatch:
```

### **Scheduled deployments**
Example cron included:

```
schedule:
  - cron: "0 3 * * 0"   # Weekly Sunday 03:00 UTC
```

This can be adjusted to:

- nightly
- hourly (for dev)
- weekly (for production)

✔ Fully configurable schedule.
