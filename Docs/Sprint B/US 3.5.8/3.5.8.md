---

# **2. Backup Strategy Overview**
The backup system consists of **three GitHub Actions pipelines**, each serving a different purpose:

| Workflow | Purpose | Frequency | Retention |
|---------|---------|-----------|-----------|
| **Daily Full Backup** | Complete database copy | Daily at 02:00 UTC | 30 days |
| **Incremental Backup** | Minimize RPO by saving deltas | Every 15 minutes | 7 days |
| **Backup Verify + Restore Test** | Validate full backup integrity | Manual or weekly | 7 days |

All backups are safely stored as **GitHub Artifacts**, which are encrypted and redundantly stored (off‑site safe).

---

# **3. Backup Mechanism**

## **3.1 Full Backup**
- Runs daily at 02:00 UTC  
- Uses:
  ```
  ./scripts/backup-db.sh --type full --out backup_out
  ```
- Outputs:
  - `*.sqlite.gz`
  - `*.sha256`
  - `manifest-*.json`

## **3.2 Incremental Backup**
- Runs every 15 minutes  
- Uses:
  ```
  ./scripts/backup-db.sh --type incremental
  ```

## **3.3 Restore Verification**
- Creates an **ephemeral SQLite DB**
- Seeds it with sample data  
- Runs the backup script  
- Restores the backup  
- Validates using:
  ```
  PRAGMA integrity_check;
  SELECT COUNT(*) FROM demo;
  ```

# **6. RPO & WRT Justification**

## ✔ **RPO = 15 minutes**
Incremental backups run every 15 minutes, meaning **max data loss = 15m**.

## ✔ **WRT ≈ 1 minute (validated)**
Restore test workflow completed in **22 seconds**, well below the 2‑hour allowed incident window.

---

# **7. Backup & Restore Procedures**

## **7.1 Backup Procedure**
1. Workflow triggers  
2. Database detected / seeded  
3. Backup script runs  
4. Output compressed + hashed  
5. Artifacts uploaded  

## **7.2 Restore Procedure**
1. Download the latest full backup  
2. Decompress using `gunzip`  
3. Load into the DB engine  
4. Validate DB state  
5. Resume services
